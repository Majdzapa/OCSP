= Native Server-Level Mutual TLS (mTLS) & Hot-Reloaded Trusted CAs
:toc:
:toclevels: 3

This technical guide explains **native server-level Mutual TLS (mTLS)** inside `ocsp-responder` (Spring Boot / embedded Tomcat) with a **zero-restart hot-reloaded `X509TrustManager`**, without relying on reverse-proxy client-certificate headers.

== 1. Architecture: Why Native Server-Level mTLS

Instead of terminating mTLS at an external proxy and forwarding headers, `ocsp-responder` terminates mTLS directly inside Tomcat (`lu.incert.ocsp.trust.tls`):

* **Zero Header-Spoofing Surface**: `ClientCertificateAuthFilter` reads **exclusively** from the native servlet TLS attribute `jakarta.servlet.request.X509Certificate` populated directly by Tomcat's SSL engine—never from HTTP headers.
* **Zero-Restart Hot-Reload (`HotReloadableTrustManager`)**: Implements `javax.net.ssl.X509TrustManager` backed directly by `TrustedCaService.getActiveTrustedCas()` (a `CopyOnWriteArrayList<X509Certificate>` synchronized with MariaDB `trusted_cas`).
* **Browser Certificate Picker Filtering**: Tomcat/JSSE calls `HotReloadableTrustManager.getAcceptedIssuers()` during every TLS `CertificateRequest`, advertising the exact list of currently enabled Trusted CA DNs so the browser filters its certificate picker automatically.
* **Graceful Fallback (`certificateVerification="optional"`)**: Tomcat uses TLS `WANT` mode (`optional`). If a user selects a trusted, user-linked certificate, `POST /api/v1/auth/login/mtls` issues an HS256 Bearer JWT immediately; if no certificate is presented or it isn't linked, `/login` falls back cleanly to Username/Password (`SELF_MANAGEMENT`) or Keycloak (`KEYCLOAK`).

== 2. End-to-End Native mTLS Flow

[source]
----
Browser (OS/Browser Cert Store)                  ocsp-responder (Tomcat Native HTTPS mTLS)
             │                                                         │
             │─── 1. TLS Handshake (HTTPS, security.tls.https-port) ──▶│
             │◀── 2. ServerHello + CertificateRequest                  │
             │       (Issuers = HotReloadableTrustManager              │
             │                  .getAcceptedIssuers())                 │
             │   [Browser filters & shows matching client certs]       │
             │─── 3. ClientCert + CertificateVerify ──────────────────▶│
             │                                                         │ 4. HotReloadableTrustManager:
             │                                                         │    PKIX chain check vs live
             │                                                         │    TrustedCaService CAs
             │─── 5. POST /api/v1/auth/login/mtls ────────────────────▶│
             │                                                         │ 6. ClientCertificateAuthFilter:
             │                                                         │    reads native servlet attr
             │                                                         │    jakarta.servlet.request.X509Certificate
             │                                                         │ 7. UserCertificateService:
             │                                                         │    SHA-256 lookup in user_certificates
             │                                                         │ 8. Issue HS256 Bearer JWT
             │◀─────────── 9. 200 OK { accessToken, tokenType } ───────│
             │   (If 401: /login falls back to Password or Keycloak)   │
----

== 3. Zero-Restart Truststore Hot-Reload

1. An administrator (`TRUSTED_CA_MANAGE`) imports, enables, disables, or deletes a CA (`BasicConstraints CA:TRUE`) in the Console UI (`/trusted-cas`) or via `/api/v1/admin/trusted-cas`.
2. `TrustedCaService.reloadTrustStore()` refreshes the in-memory `CopyOnWriteArrayList<X509Certificate>` and publishes `TrustedCasReloadedEvent`.
3. `TomcatNativeMtlsConfig.onTrustedCasReloaded(...)` invokes `protocol.reloadSslHostConfigs()` on the live Tomcat HTTPS connector.
4. All subsequent TLS handshakes immediately advertise and validate against the updated Trusted CA set—**zero JVM restart required**.

== 4. Server Configuration (`application*.yml`)

The native Tomcat HTTPS mTLS connector (`TomcatNativeMtlsConfig`) is activated when both `security.tls.client-cert-auth-enabled=true` and `security.tls.key-store` are configured (while the standard HTTP connector remains available for public RFC 6960 `/ocsp` traffic):

[source,yaml]
----
security:
  tls:
    enabled: true
    client-cert-auth-enabled: ${SECURITY_TLS_CLIENT_CERT_AUTH_ENABLED:true}
    https-port: ${SECURITY_TLS_HTTPS_PORT:8443}
    key-store: ${SECURITY_TLS_KEYSTORE:file:/certs/server/server-keystore.p12}
    key-store-password: ${SECURITY_TLS_KEYSTORE_PASSWORD:}
    key-store-type: ${SECURITY_TLS_KEYSTORE_TYPE:PKCS12}
----

== 5. REST API Endpoints

[cols="1,2,2,3",options="header"]
|===
| Method | Endpoint | Required Permission | Description
| `POST` | `/api/v1/auth/login/mtls` | Public (Native TLS cert) | Authenticates Tomcat-verified client cert against `user_certificates` and returns a Bearer JWT
| `GET` | `/api/v1/admin/trusted-cas` | `TRUSTED_CA_READ` | List all Trusted CAs and expiry/trust status
| `POST` | `/api/v1/admin/trusted-cas` | `TRUSTED_CA_MANAGE` | Import a CA PEM (`CA:TRUE`) and hot-reload Tomcat truststore immediately
| `PUT` | `/api/v1/admin/trusted-cas/\{id\}/enabled` | `TRUSTED_CA_MANAGE` | Enable or disable a Trusted CA and hot-reload immediately
| `DELETE` | `/api/v1/admin/trusted-cas/\{id\}` | `TRUSTED_CA_MANAGE` | Remove a Trusted CA and hot-reload immediately
| `GET` | `/api/v1/admin/users/\{id\}/certificates` | `USER_MANAGE` | List X.509 client certificates assigned to a user
| `POST` | `/api/v1/admin/users/\{id\}/certificates` | `USER_MANAGE` | Assign a Trusted-CA-issued X.509 certificate to a user
| `DELETE` | `/api/v1/admin/users/\{id\}/certificates/\{certId\}` | `USER_MANAGE` | Remove a user certificate assignment
|===
