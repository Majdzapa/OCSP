= System Architecture, Clean Configuration & Use Cases
:toc:

The Incert OCSP Subsystem v5.0 separates CA lifecycle operations (`kms-simulator`) from high-throughput RFC 6960 status answering (`ocsp-responder`) and cryptographic client verification (`ocsp-client`). All inter-service state synchronization happens asynchronously over RabbitMQ mTLS without any REST call between OCSP and KMS.

== Clean Package Structure (`ocsp-responder`)

[cols="1,3", options="header"]
|===
| Package | Responsibility

| `com.company.incert.ocsp.usecase`
| Reusable domain actions shared across multiple services:

| `com.company.incert.ocsp.service`
| Core domain logic: `OcspResponderService` (RFC 6960 ASN.1 DER request/response engine), `CertificateStatusService` (strict 3-tuple `CertID` lookup and monotonic sequence guard), `SigningCertificateService` (HSM CSR generation, public-key match verification, post-commit activation), `SigningCertificateValidityService` (daily validity check, 3-day alert report, 1-click renewal CSR), and `OutboxReconciliationService` (RabbitMQ manifest diffing and self-healing replay).

| `com.company.incert.ocsp.signing`
| `OcspSigner` interface, `Pkcs11OcspSigner` (SoftHSM2 PKCS#11 multi-CA signer with on-demand keypair generation and `CertID`-aware signer selection), and `SoftwareKeyOcspSigner` (non-prod fallback when `hsm.enabled=false`).

| `com.company.incert.ocsp.messaging`
| `CertificateStatusListener`, `CertificateStatusConsumerService` (idempotent inbox consumer), `InboxFailureRecorder` (`Propagation.REQUIRES_NEW` failure persistence with `AmqpHeaders.MESSAGE_ID` and `AmqpHeaders.DELIVERY_TAG`), `OutboxManifestEvent`, and `ReconciliationCommandMessage`.

| `com.company.incert.ocsp.controller`
| `OcspResponderController` (`/ocsp`), `AuthController`, `AdminDashboardController`, `SigningCertificateController`, `InboxAdminController`, `CertCheckController`, and `RevocationFeedController`.

== Strict RFC 6960 `CertID` Matching (No Serial-Only Fallback)

In RFC 6960 §4.1.1, a certificate is uniquely identified by its `CertID`:

[source]
----
CertID ::= SEQUENCE {
    hashAlgorithm       AlgorithmIdentifier,
    issuerNameHash      OCTET STRING, -- Hash of issuer's DN
    issuerKeyHash       OCTET STRING, -- Hash of issuer's public key
    serialNumber        CertificateSerialNumber
}
----

`CertificateStatusService.findByCertId(byte[] issuerNameHash, byte[] issuerKeyHash, byte[] serialNumber)` queries:

[source,java]
----
repository.findByIssuerNameHashAndIssuerKeyHashAndSerialNumber(
        issuerNameHash, issuerKeyHash, canonicalSerial);
----

* If all 3 fields match a row in `ocsp.revocation_status`, the responder returns `GOOD` or `REVOKED` signed by the matching CA's delegated OCSP signing certificate.
* If the caller provides an Issuer CA PEM that did **not** issue the target certificate (so `issuerNameHash` or `issuerKeyHash` differs), the 3-tuple query returns `Optional.empty()` and the OCSP responder returns **`UNKNOWN`** — even if a certificate with the same serial number exists under another CA.
