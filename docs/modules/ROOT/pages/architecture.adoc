= System Architecture, Clean Configuration & Use Cases
:toc:

The Incert OCSP Subsystem v5.0 separates CA lifecycle operations (`kms-simulator`) from high-throughput RFC 6960 status answering (`ocsp-responder`) and cryptographic client verification (`ocsp-client`). All inter-service state synchronization happens asynchronously over RabbitMQ mTLS without any REST call between OCSP and KMS.

== Domain-Grouped Modular Monolith Structure (`com.company.incert.ocsp.*`)

Domain boundaries and cycle-freedom are enforced automatically at test time via **ArchUnit** (`ArchitectureBoundaryTest`):

[cols="1,3", options="header"]
|===
| Domain Package | Responsibility

| `auth`
| Authentication (`AuthenticationService`, `SecurityConfig` with 3 ordered `SecurityFilterChain`s), `SecurityPermissions` + `OcspPermissionEvaluator` (`hasPermission`), `LocalIdentityService`, `UserCertificateService`, `ClientCertificateAuthFilter`, and stateless `KeycloakJwtAuthenticationConverter`.

| `trust`
| Hot-reloaded mTLS Trusted CA truststore (`TrustedCaService`, `TrustedCaController`, `trusted_cas` table) verifying user certificates with zero application restart.

| `responder`
| Public RFC 6960 `/ocsp` endpoint (`OcspResponderController`, `OcspResponderService`, `OcspResponderProperties`) — direct signing with no response cache.

| `signing`
| In-process PKCS#11 (`ipkcs11wrapper`) multi-CA signers (`MultiProviderOcspSigner`, `Pkcs11Engine`, `SoftwareKeyOcspSigner`), `SigningCertificateService`, `SigningCertificateValidityService`, and `FindSigningCertificateUseCase`.

| `status`
| Certificate revocation status inventory (`CertificateStatusService`, `CertificateStatusUpdateCommand`, `RevocationStatusRepository`, `CertCheckController`, `RevocationFeedController`).

| `rabbitmq`
| RabbitMQ mTLS topology (`RabbitMqConfig`), `CertificateStatusConsumerService`, `InboxFailureRecorder`, `InboxAdminController`, and batched `OutboxReconciliationService`.

| `dashboard`
| Cross-domain administrative metrics aggregator (`AdminDashboardController`).

| `schedule`
| Centralized `@Scheduled` job runner (`ScheduledJobsConfig`).

| `shared`
| Cross-cutting properties (`AppSecurityProperties`, `ScheduledJobsProperties`), `ProductionSecretsValidator`, `PatternValidation`, `CanonicalizeSerialHexUseCase`, `JacksonConfig`, and `OpenApiConfig`.
|===

== Strict RFC 6960 `CertID` Matching (No Serial-Only Fallback)

In RFC 6960 §4.1.1, a certificate is uniquely identified by its `CertID`:

[source]
----
CertID ::= SEQUENCE {
    hashAlgorithm       AlgorithmIdentifier,
    issuerNameHash      OCTET STRING, -- Hash of issuer's DN
    issuerKeyHash       OCTET STRING, -- Hash of issuer's public key
    serialNumber        CertificateSerialNumber
}
----

`CertificateStatusService.findByCertId(byte[] issuerNameHash, byte[] issuerKeyHash, byte[] serialNumber)` queries:

[source,java]
----
repository.findByIssuerNameHashAndIssuerKeyHashAndSerialNumber(
        issuerNameHash, issuerKeyHash, canonicalSerial);
----

* If all 3 fields match a row in `ocsp.revocation_status`, the responder returns `GOOD` or `REVOKED` signed by the matching CA's delegated OCSP signing certificate.
* If the caller provides an Issuer CA PEM that did **not** issue the target certificate (so `issuerNameHash` or `issuerKeyHash` differs), the 3-tuple query returns `Optional.empty()` and the OCSP responder returns **`UNKNOWN`** — even if a certificate with the same serial number exists under another CA.
