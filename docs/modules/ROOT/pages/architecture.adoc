= System Architecture & Data Flow
:toc:

The Incert OCSP Subsystem is designed as a decoupled, event-driven monolith combining high-throughput direct query handling with robust asynchronous synchronization.

== High-Level Architecture

The architecture decouples the certificate authority / Key Management Service (KMS) lifecycle from relying party OCSP verification:

[source]
----
                   ┌─────────────────────────────────────────┐
                   │             Relying Parties             │
                   │     (Browsers, CLI, OpenSSL, curl)      │
                   └──────────────────┬──────────────────────┘
                                      │ RFC 6960 (POST / GET)
                                      ▼
                   ┌─────────────────────────────────────────┐
                   │             OCSP Responder              │
                   │               (Port 8080)               │
                   │  ┌───────────────────────────────────┐  │
                   │  │   Direct DB Certificate Lookup    │  │
                   │  └─────────────────┬─────────────────┘  │
                   │                    │                    │
                   │  ┌─────────────────▼─────────────────┐  │
                   │  │   PKCS#11 Delegated OCSP Signer   │  │

                   └────────────────────┼────────────────────┘
                                        │ SunPKCS11
                                        ▼
                   ┌─────────────────────────────────────────┐

== Core Architectural Patterns

=== 1. Interface & Adapter Pattern for Pluggability
To ensure flexibility without the over-engineering of pure hexagonal architecture:
* **HSM Signing**: Defined by the `OcspSigner` interface. The `Pkcs11OcspSigner` implementation communicates with SoftHSM2 or physical HSM appliances (e.g. Thales Luna, Utimaco, AWS CloudHSM). To migrate to another HSM, only the adapter is changed.
* **Messaging**: Defined by `CertificateStatusEventPublisher` and `CertificateStatusConsumer`. The RabbitMQ implementation can be switched to Kafka, AWS SQS, or Azure Service Bus by providing a new adapter bean.

=== 2. Transactional Outbox Pattern
The KMS Simulator records certificate status changes and outbox events in a single database transaction:
1. `kms_certificates` record is created or updated (`GOOD`, `REVOKED`).
2. An event is written to `kms_outbox` with status `PENDING`.
3. A background relay polls `PENDING` outbox records and publishes them to RabbitMQ over mutual TLS.
4. On acknowledgment, outbox state is updated to `PUBLISHED`.

=== 3. Idempotent Inbox Consumer & Deduplication
The OCSP Responder processes status update events via an inbox table:
* Each event is identified by an idempotent `eventId`.
* Duplicate messages are identified, logged, and marked `DUPLICATE` without corrupting certificate status.
* Poison messages that fail deserialization or processing are automatically rejected (`requeue = false`) and routed to the Dead Letter Queue (`ocsp.certificate.status.dlq`).

=== 4. Direct In-Memory & Read-Optimized DB Lookups
Unlike distributed microservice querying:
* The OCSP Responder reads local database state (`ocsp.certificate_status`) with indexed serial numbers.
* High cache locality ensures sub-millisecond query evaluation.
* The PKCS#11 signer retains in-memory session pools to the HSM slot, eliminating connection latency.
