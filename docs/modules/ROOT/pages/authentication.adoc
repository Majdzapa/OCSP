= Authentication, SecurityPermissions & Ordered Filter Chains
:toc:

The OCSP Responder supports two independent authentication modes configured via `app.auth.mode` (`SELF_MANAGEMENT` or `KEYCLOAK`), with **no cross-system user synchronization**, plus fine-grained **`hasPermission(...)`** RBAC powered by the `SecurityPermissions` enum.

== 1. Authentication Modes (`app.auth.mode`)

[cols="1,2,2",options="header"]
|===
| Mode | Identity & Credentials | How It Works
| `SELF_MANAGEMENT` | Application DB (`ocsp.users`, `ocsp.user_roles`) | `LocalIdentityService` manages UUID users with BCrypt password hashes, `PatternValidation`, and password reset. `AuthenticationService` delegates login to Spring Security's `AuthenticationManager`.
| `KEYCLOAK` | Keycloak OIDC (`incert` realm) | `KeycloakJwtAuthenticationConverter` statelessly extracts `sub`, `preferred_username`, `email`, `name`, `realm_access.roles`, and `groups` directly from the verified JWT into `InternalPrincipal` with zero DB writes.
|===

Both modes (and optional mTLS client certificates) resolve to the exact same `InternalPrincipal` (`userId`, `username`, `email`, `fullName`, `tenantId`, `authSource`, `roles`).

== 2. Ordered SecurityFilterChains (`SecurityConfig`)

1. **`@Order(1)` Public OCSP & Probes**: `/ocsp`, `/ocsp/**`, `/actuator/health`, `/actuator/info`, `/v3/api-docs/**`, `/swagger-ui/**` — stateless, zero auth overhead.
2. **`@Order(2)` Authentication Boundary**: `/api/v1/auth/**` — `/config`, `/me`, `/login`.
3. **`@Order(3)` Protected Admin & Business Plane**: `/api/v1/admin/**` — requires authentication; fine-grained authorization is enforced on every controller method via `@PreAuthorize("hasPermission(null, '<PERMISSION>')")`.

== 3. Fine-Grained RBAC (`SecurityPermissions` + `hasPermission`)

`OcspPermissionEvaluator` (registered on `MethodSecurityExpressionHandler`) evaluates `hasPermission(null, '<PERMISSION>')` against the `SecurityPermissions` enum:

[cols="2,1,1,1",options="header"]
|===
| `SecurityPermissions` | `ROLE_ADMIN` | `ROLE_AGENT` / `ROLE_OPERATOR` | `ROLE_AUDITOR`
| `DASHBOARD_READ`, `REVOCATION_READ`, `INBOX_READ`, `CERT_CHECK_READ`, `SIGNING_CERT_READ`, `TRUSTED_CA_READ` | Allowed | Allowed | Allowed
| `SIGNING_CERT_CREATE_CSR`, `SIGNING_CERT_IMPORT`, `SIGNING_CERT_VALIDITY_CHECK`, `SIGNING_CERT_RENEW`, `INBOX_REPLAY` | Allowed | Allowed | Denied
| `SIGNING_CERT_ACTIVATE`, `SIGNING_CERT_DEACTIVATE`, `SIGNING_CERT_DELETE` | Allowed | Denied | Denied
| `TRUSTED_CA_MANAGE`, `USER_READ`, `USER_MANAGE` | Allowed | Denied | Denied
|===

== 4. Production Secrets Validation (`ProductionSecretsValidator`)

Base `application.yml` contains no hardcoded default secrets (dev defaults live strictly in `application-dev.yml` and `application-local.yml`). Outside `dev`, `local`, or `test` profiles, `ProductionSecretsValidator` refuses startup if any required secret is blank or matches a known development default.
