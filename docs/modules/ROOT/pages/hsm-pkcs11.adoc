= Multi-Device PKCS11J, PkcsProviders & gRPC Signing
:toc:

The OCSP Responder decouples RFC 6960 response signing from cryptographic devices using a **Ports & Adapters** architecture supporting multiple simultaneous HSMs, USB tokens, and SoftHSM2 slots via custom `pkcs11j` JNI bindings and gRPC.

Private keys are generated with `CKA_EXTRACTABLE = FALSE` and never leave the token boundary.

== Architecture: Ports, `PkcsProviders`, `PKCS11J` & gRPC

[source]
----
ocsp-responder (pure Java)
 └── OcspSigner (MultiProviderOcspSigner — per-CA certificate & device routing)
      └── PkcsProviders (registry keyed by providerId)
           ├── GrpcCryptoProviderAdapter  ──(gRPC / optional mTLS :9090)──▶ hsm-signer daemon
           │                                                                 ├── PkcsProviders (ref-counted modules)
           │                                                                 ├── Pkcs11SessionPool (CK_SESSION_HANDLEs)
           │                                                                 └── pkcs11j (Pkcs11LibraryPort + libpkcs11j.so)
           │                                                                      └── C_Initialize -> C_OpenSession -> C_Login
           │                                                                          C_GenerateKeyPair -> C_CreateObject
           │                                                                          C_SignInit -> C_Sign -> C_Finalize
           └── SunPkcs11CryptoProviderAdapter (optional local fallback)
----

* **`Pkcs11LibraryPort` (`pkcs11j`)**: Clean port interface mapping 1:1 to OASIS PKCS#11 v2.40 Cryptoki C APIs (`C_Initialize` with `CKF_OS_LOCKING_OK`, `C_GetSlotList`, `C_GetTokenInfo`, `C_OpenSession`, `C_Login`, `C_FindObjects*`, `C_GetAttributeValue`, `C_GenerateKeyPair`, `C_CreateObject`, `C_SignInit`, `C_Sign`, `C_Logout`, `C_CloseSession`, `C_Finalize`).
* **`PkcsProviders` (module ref-counting & multi-device registry)**: Calls `C_Initialize` once per `.so`/`.dylib` path (`CKR_CRYPTOKI_ALREADY_INITIALIZED` handled gracefully), pools thread-safe RO sessions per slot in `Pkcs11SessionPool`, and allows multiple devices (`softhsm-primary`, `softhsm-secondary`, vendor HSMs) to run concurrently.
* **`CryptoProviderPort` (`ocsp-responder`)**: High-level port decoupling `ocsp-responder` from native drivers. Statically isolates `libpkcs11j` and vendor `.so` drivers inside `hsm-signer` behind a stateless gRPC contract (`hsm-signer-proto`).

== Zero Pre-Seeded Keys at Startup

In Docker Compose, `hsm/init-hsm.sh` initializes two empty SoftHSM2 tokens (`ocsp-signing` for `softhsm-primary` and `ocsp-signing-2` for `softhsm-secondary`) if they do not already exist:

[source,bash]
----
softhsm2-util --init-token --free \
  --label "${HSM_TOKEN_LABEL}" \
  --so-pin "${HSM_SO_PIN}" \
  --pin "${HSM_PIN}"
----

* **No keypair or self-signed certificate is generated on startup.**
* When `ocsp-responder` boots before any signing certificate is activated, OCSP requests answer deterministically with RFC 6960 `OCSPRespBuilder.TRY_LATER (3)`.

== On-Demand Keypair Generation, CSR & Multi-Device Selection

Operators provision signing keys and certificates per device via the Admin Console (`http://localhost:3002/signing-certificates`) or REST API:

1. **Discover Connected Signing Devices** (`GET /api/v1/admin/signing-certificates/providers` and `/hsm-info`):
   * Lists every active provider (`providerId`, `providerType`, `tokenLabel`, `slotId`, `healthy`, and key labels per device).
2. **Generate Keypair & PKCS#10 CSR on Selected Device** (`POST /api/v1/admin/signing-certificates/csr`):
   * Pass `providerId` (e.g. `softhsm-primary` or `softhsm-secondary`), `keyLabel`, `keyAlgorithm` (`RSA` or `EC`), `keySize`, and `reuseExistingKey`.
   * Inside `hsm-signer`, `Pkcs11Provider.generateKeyPair` invokes `C_GenerateKeyPair` directly (`CKA_SENSITIVE=true`, `CKA_EXTRACTABLE=false`) without creating dummy certificates, then signs the PKCS#10 CSR via `C_SignInit` / `C_Sign` (converting ECDSA raw `r || s` output to ASN.1 DER automatically).
3. **Sign CSR in KMS Simulator** (`http://localhost:3001/certificates`):
   * Select the target CA, paste the CSR PEM, and issue with profile **`OCSP_SIGNING`** (`basicConstraints = CA:FALSE`, `extendedKeyUsage = id-kp-OCSPSigning`).
4. **Import & Public Key Verification** (`POST /api/v1/admin/signing-certificates`):
   * Supply `providerId`, `keyLabel`, and `certificatePem`.
   * `Pkcs11Provider.importCertificate` verifies that the certificate public key matches the token's public key before storing the `CKO_CERTIFICATE` object via `C_CreateObject`.
   * Flyway migration `V13` persists `provider_id` in `ocsp.signing_certificates`.
5. **Post-Commit Activation & Multi-CA/Multi-Device Routing** (`PUT /api/v1/admin/signing-certificates/\{id\}/activate`):
   * `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)` updates `MultiProviderOcspSigner`.
   * Before signing each OCSP response, `selectSigner(CertificateID)` matches the request's issuing CA (`IssuerNameHash` + `AuthorityKeyIdentifier`) to its active signing certificate and routes signing to that certificate's assigned `providerId` and `keyLabel` in 1 gRPC round-trip.

== Adding External Hardware HSMs or Multiple `hsm-signer` Hosts

* **Multiple local tokens/vendors in one `hsm-signer` instance**: Add entries under `hsm-signer.providers[]` with each device's `id`, `library-path` (e.g. Utimaco `/opt/utimaco/libcs_pkcs11_R2.so`, Thales Luna `/usr/safenet/lunaclient/lib/libCryptoki2_64.so`, YubiHSM), `token-label` or `slot-id`, `pin`, and `prehash-in-jvm`.
* **Multiple remote `hsm-signer` servers**: Add entries under `hsm.grpc.endpoints[]` in `ocsp-responder` (`host`, `port`, optional `id-prefix`, and optional PKCS#12 mTLS `key-store` / `trust-store`). All discovered providers appear simultaneously in `PkcsProviders` and the Admin Console.
