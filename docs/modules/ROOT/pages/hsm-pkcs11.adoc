= SoftHSM2 PKCS#11 On-Demand HSM Signing
:toc:

The OCSP Responder performs all cryptographic response signing inside a SoftHSM2 PKCS#11 token (`ocsp-signing`). Private keys are generated with `CKA_EXTRACTABLE = FALSE` and never leave the HSM boundary.

== Zero Pre-Seeded Keys at Startup

In v5.0, `hsm/init-hsm.sh` initializes only an **empty** SoftHSM2 token (`ocsp-signing`) if one does not already exist:

[source,bash]
----
softhsm2-util --init-token --free \
  --label "${HSM_TOKEN_LABEL}" \
  --so-pin "${HSM_SO_PIN}" \
  --pin "${HSM_PIN}"
----

* **No keypair or self-signed certificate is generated on startup.**
* When `ocsp-responder` boots against an unprovisioned HSM token, `Pkcs11OcspSigner` starts in an unconfigured state and logs:
  `No signing key in HSM token 'ocsp-signing'. Generate a CSR, have it signed by your CA, then import and activate the certificate. OCSP requests answer tryLater until then.`
* Any RFC 6960 request received before a signing certificate is activated receives a compliant `OCSPRespBuilder.TRY_LATER (3)` response.

== On-Demand HSM Keypair & PKCS#10 CSR Workflow

Operators provision signing keys and certificates through the Admin Console (`http://localhost:3002/signing-certificates`) or REST API:

1. **Generate HSM Keypair & CSR** (`POST /api/v1/admin/signing-certificates/csr`):
   * Supports `RSA` (`2048`, `3072`, `4096`) and `EC` (`256` / `secp256r1`, `384` / `secp384r1`).
   * If `reuseExistingKey` is `false` (or the key label does not exist yet), `Pkcs11OcspSigner` generates a new non-extractable keypair directly inside the SoftHSM2 token under the requested `keyLabel` along with a minimal self-signed bootstrap certificate object so SunPKCS11 exposes the private key entry.
   * Builds and signs a PKCS#10 Certificate Signing Request (`-----BEGIN CERTIFICATE REQUEST-----`) inside the HSM.
2. **Sign CSR in KMS Simulator** (`http://localhost:3001/certificates`):
   * In KMS, select the target Root or Subordinate CA, paste the CSR PEM, and select profile **`OCSP_SIGNING`** (which adds `basicConstraints = CA:FALSE` and `extendedKeyUsage = id-kp-OCSPSigning` OID `1.3.6.1.5.5.7.3.9`).
3. **Import & Public Key Verification** (`POST /api/v1/admin/signing-certificates`):
   * `Pkcs11OcspSigner.importCertificateToToken(keyLabel, holder)` compares the uploaded X.509 certificate's `SubjectPublicKeyInfo` bytes against the HSM keypair's public key before binding the certificate to the PKCS#11 entry.
   * If the certificate was signed for a different keypair, import fails immediately with a clear `IllegalArgumentException`.
4. **Post-Commit Activation** (`PUT /api/v1/admin/signing-certificates/\{id\}/activate`):
   * Marks the certificate active in `ocsp.signing_certificates` and publishes `SigningConfigurationChangedEvent`.
   * `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)` updates the in-memory `Pkcs11OcspSigner` table only after the database transaction commits.

== Multi-CA Signer Selection (`selectSigner(CertificateID)`)

Multiple signing certificates (one per issuing CA) can be active simultaneously. When an OCSP request arrives, `Pkcs11OcspSigner.selectSigner(CertificateID requestCertId)` selects the active, non-expired signing certificate whose `subjectNameHash` / `publicKeyHash` or `issuerNameHash` matches the requested `CertID`, ensuring multi-CA RFC 6960 §4.2.2.2 compliance.
