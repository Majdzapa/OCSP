= Multi-Device PKCS#11 (`ipkcs11wrapper`), DB Providers & Pattern 2 Runtime Activation
:toc:

The OCSP Responder uses Maven Central's **`org.xipki:ipkcs11wrapper`** JAR (zero custom C compilation or native build scripts) embedded directly in `ocsp-responder` behind a **Ports & Adapters** architecture supporting multiple simultaneous HSM drivers (`libraryPath` + `libraryWrapperPath`) and token slots (`crypto_providers` + `crypto_devices` in MariaDB) with **zero PINs stored in the database or retained in RAM**.

Private keys are generated with `CKA_EXTRACTABLE = FALSE` and never leave the token boundary.

== Architecture: `Pkcs11Engine` (`ipkcs11wrapper`), DB Tables & `PkcsProviders`

[source]
----
ocsp-responder (Modular Monolith)
 ├── signing.hsm.MultiProviderOcspSigner     (per-CA IssuerNameHash + AKI matching)
 ├── signing.provider.PkcsProviders          (multi-device runtime registry)
 │    ├── Pkcs11jCryptoProviderAdapter       (Pattern 2 LOCKED <-> ACTIVE lifecycle)
 │    │    └── signing.pkcs11.Pkcs11Engine   (org.xipki:ipkcs11wrapper -> C_Initialize/C_Login/C_Sign/C_Finalize)
 │    └── Custom CryptoDeviceAdapterFactory  (extensible for KMS, KMIP, Cloud HSM, FFM, etc.)
 ├── signing.provider.LibraryPathAllowlist   (prevents arbitrary dlopen() outside hsm.allowed-library-dirs)
 └── MariaDB Tables (Flyway V14)
      ├── crypto_providers                   (wrapper_type, library_path, library_wrapper_path)
      └── crypto_devices                     (device_id, provider_id FK, token_label / slot_id — NO PIN)
----

* **`Pkcs11LibraryPort` (`signing.pkcs11`)**: Port interface backed by `XiPkiPkcs11Library` (`org.xipki:ipkcs11wrapper`), mapping 1:1 to OASIS PKCS#11 v2.40 Cryptoki APIs (`C_Initialize` with `CKF_OS_LOCKING_OK`, `C_GetSlotList`, `C_GetTokenInfo`, `C_OpenSession`, `C_Login`, `C_FindObjects*`, `C_GetAttributeValue`, `C_GenerateKeyPair`, `C_CreateObject`, `C_SignInit`, `C_Sign`, `C_Logout`, `C_CloseSession`, `C_Finalize`).
* **`libraryPath` vs `libraryWrapperPath`**:
  ** `library_path`: Per-vendor Cryptoki `.so`/`.dylib` driver (e.g. `/usr/lib/softhsm/libsofthsm2.so`, Thales Luna `/usr/safenet/lunaclient/lib/libCryptoki2_64.so`, Utimaco `/opt/utimaco/libcs_pkcs11_R2.so`). Multiple drivers and slots run simultaneously inside `PkcsProviders`.
  ** `library_wrapper_path`: Explicit allowlisted host path to the JNI wrapper binary (defaults to `/opt/pkcs11j/libpkcs11wrapper.so`, pre-staged inside `ocsp-responder` at `/opt/pkcs11j/libpkcs11wrapper.so`).
* **`LibraryPathAllowlist`**: Refuses relative paths, `..` traversal, and any library or wrapper path outside `hsm.allowed-library-dirs` (`HSM_ALLOWED_LIBRARY_DIRS`).

== Pattern 2: Runtime Activation (Zero PIN in DB & RAM)

At startup, `DatabaseCryptoProviderLoader` reads `crypto_providers` and `crypto_devices` from MariaDB and registers every enabled device in **`LOCKED`** state without opening PKCS#11 sessions or requiring a PIN.

* When all devices are `LOCKED`, `ocsp-responder` still starts healthy (`cryptoDevicesHealthIndicator` reports `UP`) and answers OCSP requests deterministically with RFC 6960 `TRY_LATER (3)` until unlocked and paired with an active signing certificate.
* Administrators unlock a device via **HSM Devices** (`http://localhost:3002/hsm-devices`) or `POST /api/v1/admin/crypto-devices/\{deviceId\}/activate` with `{"pin": "..."}`:
  1. Validates `library_path` and `library_wrapper_path` against `LibraryPathAllowlist`.
  2. Opens pooled sessions and executes `C_Login(CKU_USER, pin)`.
  3. **Immediately wipes the PIN `char[]` buffer** in both `Pkcs11SessionPool` and the REST controller (`finally` block). No copy of the PIN stays in RAM or DB.
* Administrators can lock a device anytime (`POST /api/v1/admin/crypto-devices/\{deviceId\}/deactivate`), executing `C_Logout` and closing pooled sessions.
* If the underlying HSM token logs out the session (`CKR_USER_NOT_LOGGED_IN`), `Pkcs11SessionPool` does not attempt silent re-login; the device flips back to `LOCKED` and awaits admin unlock.

== Provisioning Keys, CSRs & Multi-Device Signing

1. **Manage Providers & Unlock Device**:
   * Open `HSM Devices` in `ocsp-console` (`/hsm-devices`) or `GET /api/v1/admin/crypto-providers` and `GET /api/v1/admin/crypto-devices`.
   * Click **Unlock (PIN)** on `softhsm-primary` or `softhsm-secondary`.
2. **Generate Keypair & PKCS#10 CSR** (`POST /api/v1/admin/signing-certificates/csr`):
   * Select `providerId`, `keyLabel`, `keyAlgorithm` (`RSA` or `EC`), `keySize`, and `reuseExistingKey`.
   * `Pkcs11Provider.generateKeyPair` invokes `C_GenerateKeyPair` directly (`CKA_SENSITIVE=true`, `CKA_EXTRACTABLE=false`) and signs the CSR via `C_SignInit` / `C_Sign`.
3. **Import & Activate Certificate**:
   * Issue the certificate from the CA (with `OCSPSigning` EKU), import via `POST /api/v1/admin/signing-certificates` (`providerId` saved in `signing_certificates.provider_id`), and activate via `PUT /api/v1/admin/signing-certificates/\{id\}/activate`.
   * Before signing each OCSP response, `MultiProviderOcspSigner.selectSigner(CertificateID)` matches the request's issuing CA (`IssuerNameHash` + `AuthorityKeyIdentifier`) and routes signing in-process to the assigned `providerId` and `keyLabel`.
